# Director engineering rules

## Scope and user experience
- The focused optimized H3 task permits only the frozen four-file DmitryDB native NVFP4 recipe after explicit in-app license/territory acknowledgement and Confirm. Reuse the pinned SDK, verifier, storage and native T2VA graph; no downloads or real inference in tests. Generic downloads and production provisioning retain their separate disabled gates. Ready denotes verified registration/configuration, not proven 16 GB/32 GB inference. Preserve Wan and all user media; H3 Resolve/audio handoff is not validated yet.
- The creative-studio milestone permits bounded live Hub discovery, explicit inert repository-data plans/transfers, persistent owned media/projects/history, image capability foundations and read-only pipeline inspection. Reuse the existing SDK/verifier/storage; `DIRECTOR_ENABLE_REPOSITORY_DOWNLOADS` defaults off and is never enabled by the launcher. No H3/new model weights or installed-model deletion during implementation/tests without explicit approval. A data download never registers an execution adapter. Keep production provisioning/redistribution NO-GO, the Windows runtime/models and Resolve approval boundary intact. Studio tests must use `DIRECTOR_STUDIO_ROOT`/temporary storage, never the user's Library. Uploaded media may be decoded only by the existing bounded CPU private PyAV probe; no repository code, CUDA/model execution or arbitrary shell fragments.
- Stage 13 launcher sessions generate a fresh 384-bit manager key internally. Pass it only in backend/server-proxy process environments; never expose it to the browser, VITE variables, URLs, files or logs. The explicit development launcher proxy may authenticate only marked requests with exact local Host and trusted Origin or same-origin Fetch Metadata/Referer proof. Return a non-secret session flag to the UI. Default standalone and production modes do not inject credentials. Stop clears owned session records/signals and in-memory credentials; never alter media/models or production gates.
- Stage 13 explicitly authorizes cleanup of the verified Director-owned WSL distro, obsolete experiment and disposable caches only after native dependency checks and hash-verified preservation. This supersedes earlier reference-runtime preservation instructions for those removed resources. Normal launch is Windows-only; retain source, user media, installed native runtime, compact final evidence and licenses. Production provisioning/redistribution remain NO-GO. Future cleanup requires explicit scope and ownership verification; never clear shared caches or global software.
- Stage 12 permits only the separately authorized private Windows development candidate under `runtime/windows-dev-001`, the fixed workflow and native PyAV conversion with `DIRECTOR_DEV_WINDOWS_RUNTIME=1`, and the explicit Start/Stop launcher. Preserve the complete WSL reference and experiment evidence. Production provisioning and redistribution remain NO-GO; private execution success does not change them. Never download/install from the launcher, weaken manager authentication, expose/save keys, or place clips without fresh explicit timeline approval.
- Stage 11 permits the job-associated development result chain only: fixed Wan generation, controlled existing WSL PyAV conversion, authenticated Media Pool import and explicitly confirmed timeline placement. Reuse the placement adapter; reject paths/workflows supplied by requests, prevent ambiguous mutation retries, preserve old media and all experiment evidence. No cleanup or production installer changes.
- Stage 10 permits only explicit development timeline review/placement of the verified Stage 9 clip through the separate Resolve adapter with `DIRECTOR_ENABLE_DEV_RESOLVE=1`. Require manager authentication and fresh unchecked user confirmation of the timeline target. Do not retry ambiguous insertion, import arbitrary media, change timeline/project settings, clean experiment files or enable production provisioning.
- Stage 8 explicitly permits the separate development-only fixed Wan adapter in `backend/director/generation`. Enable only with `DIRECTOR_ENABLE_DEV_GENERATION=1` and frontend development `VITE_DEV_GENERATION=1`. Only prompt/seed vary; no arbitrary workflows, custom nodes or production installer changes. Generation status/output require manager authentication; output is bounded, job-associated and checked for links/junctions. Never run real inference in automated tests. Keep native production NO-GO. Do not automatically start WSL/ComfyUI or retry ambiguous submissions.
- Director is a Windows-first local AI video assistant intended for DaVinci Resolve.
- The current implementation covers **Milestones 1 through 4C**: model management, React frontend, passive runtime diagnostics, a proposed runtime profile and offline runtime fixture provisioning. Real runtime software and weights have never been installed by Director.
- Do not start another milestone unless the user requests it. Keep real downloads disabled by default. No real runtime provisioning, ComfyUI, inference, generation, Resolve integration or external installation changes are authorized by 4C. Frontend generation, upload and real-model installation remain disabled.
- Keep explanations beginner-friendly. Explain commands, assumptions, verification results, and limitations honestly.
- Inspect existing files and preserve user changes before editing. Do not perform destructive cleanup or commit secrets.

## Architecture
- Use Python 3.11+, FastAPI, and Pydantic v2. The frontend in `frontend/` uses React/TypeScript/Vite and plain CSS with shared tokens; keep it separate from backend services.
- Keep API access in `frontend/src/api` with typed contracts, runtime response guards, abortable requests and timeouts. Unknown compatibility/hardware must stay unknown. Never substitute test fixtures for failed live requests.
- Preserve backend Host/Origin/key protections. The Vite proxy accepts only a loopback target and matching local incoming Origin before forwarding it to the backend origin. Credential injection is allowed only for the explicitly authorized Stage 13 launcher session described above; standalone proxy requests still require explicit keys.
- Manager keys entered in the UI stay in memory, never browser storage or VITE_ variables. Never embed authentication secrets in source/builds/URLs. Persist only validated job IDs in tab session storage, capped at 12. No backend job-list endpoint exists.
- 3B permits explicit fixture license acknowledgement, confirmed offline fixture installation and job cancellation. Visiting pages starts no jobs or downloads. Installation UI is restricted to fixture-tiny with DIRECTOR_ENABLE_FIXTURES=1 on the backend and development-only VITE_ENABLE_FIXTURES=1 on the frontend. Production builds hide fixtures; Generate always excludes them. Wan installation remains disabled.
- Keep hardware probes in `backend/director/system`, registry/evaluation in `backend/director/models`, and HTTP wiring in `backend/director/main.py`.
- Keep runtime profiles in `runtime_profiles/` and provisioning in `backend/director/runtimes`. Reuse existing storage locks, inventory checks, atomic records and SHA-256 verification. The runtime namespace is `.director-runtime` with its own ownership marker; never use the backend environment or external runtime as its root.
- Runtime fixture provisioning requires `DIRECTOR_ENABLE_RUNTIME_FIXTURES=1` and the existing manager authorization. Only the built-in profile digest and inert byte allowlist may provision. Real profiles remain proposed, with missing artifact metadata explicit; no flag enables real runtime installation.
- Runtime validation in 4C checks inventory, size, hash, profile identity and ownership only. Never execute an interpreter, package manager, PyTorch, CUDA or ComfyUI. `installed_unvalidated` and structural verification never imply execution validation or generation readiness. Do not relocate future real virtual environments; use final-path candidates and pointer activation.
- Runtime startup marks nonterminal jobs interrupted without resuming. Cleanup is explicit and exact-inventory scoped; unknown additions, links and ownership failures block deletion. Never recursively delete an unvalidated runtime root.
- Runtime diagnostics remain passive: inspect bounded configured metadata and fixed driver queries, never import PyTorch, initialize CUDA or execute configured interpreters/ComfyUI. Preserve unknown execution RuntimeState separately from observed package presence; generation readiness remains false. Do not expose configured paths or environment secrets.
- Preserve legacy combined installation-plan semantics. The additive artifact_review is a read-only manager preflight, not consent or generation readiness. Never ignore its blockers or reuse acknowledgements without fresh explicit review.
- Keep compatibility evaluation a pure function: no subprocesses, downloads, or inference inside it.
- Keep model management in `backend/director/installations`. Use an isolated `.director` namespace, an OS root lock, exact component allowlists and pinned commits. Never execute manifest code or manage external ComfyUI files.
- Before activation verify every required artifact's exact bytes and streaming SHA-256. Transfer progress and filename existence are not readiness. `generation_ready` remains false.
- Acknowledgements require explicit boolean acceptance of reviewed, hashed document versions. Never fabricate license text or record acceptance automatically.
- Mutation routes require a local manager key and trusted Host/Origin. Never accept/log HF credentials in request bodies, manifests or job records. Public transfers use token=False; optional login uses the SDK's supported store.
- Test with tiny synthetic fixtures and fake transports only. Do not enable real downloads in tests. Do not automatically resume transfers at startup. Repair and cache garbage collection are deferred.
- Use declarative validated JSON manifests in `model_registry/`. Never execute code from a manifest.
- Future AI runtime management and Resolve scripting must have separate adapters; neither should become an import requirement for this backend's hardware/registry tests.
- Prefer small functions and explicit schemas. Avoid speculative frameworks, databases, abstractions, or empty placeholder components.

## Hardware and metadata integrity
- Never assume NVIDIA, CUDA, a dedicated GPU, administrator privileges, or internet access.
- Unknown measurements are `None`/JSON `null`, not zero. Return warnings when a probe fails.
- Bound subprocess execution time, avoid `shell=True`, and never interpolate user input into PowerShell.
- Windows CIM AdapterRAM is an unreliable estimate. Never use it to confirm a VRAM requirement.
- Evaluate each GPU independently; never sum VRAM across GPUs.
- Distinguish failed GPU detection from a successfully detected absence of GPUs.
- Every mock manifest must have `is_mock: true`, `MOCK` in its name, fictional requirements, and no top-level Hugging Face repository id. Only the opt-in `is_fixture` mock may declare fictional component identities; it uses an offline allowlisted provider and cannot generate video.
- Do not invent model requirements, licenses, runtime support, or external API capabilities. Research primary sources before introducing real model metadata.
- A hardware match is not proof of runtime compatibility or generation success.
- Preserve the original compatibility `status` meaning; use the added `assessment` and profile checks for runtime/hardware evidence.
- Exact artifact sizes, immutable revisions, and measured requirements must not be invented from rounded sizes or publisher benchmarks. Keep unknown metadata null and estimates separate.
- Planning must remain read-only. Validate Windows-safe relative destinations and check resolved containment; never execute manifest contents.

## Verification and documentation
- Add meaningful pytest tests for behavior changes: validation errors, unknown/insufficient hardware, and API responses.
- Mock hardware probes in unit tests so tests work without a GPU or PowerShell. Use dependency overrides for endpoint tests.
- From the repository root, run `.\.venv\Scripts\python.exe -m pytest` after changes.
- From `frontend/`, run `npm.cmd test` and `npm.cmd run build` after frontend changes. Tests are offline and use backend-shaped fixtures; use `npm.cmd ci` with the committed lockfile. Keep styles readable with `npm.cmd run format:check`.
- For UI changes, inspect the actual local app and responsive layout; distinguish browser/API smoke checks from mocked component tests. Do not weaken backend security or add broad CORS to make development convenient.
- For API changes, start Uvicorn on `127.0.0.1`, make actual HTTP requests, and stop the verification process afterward.
- Report checks actually performed; distinguish mocked tests from checks on the current machine.
- Keep `README.md` and `docs/architecture.md` aligned with implemented behavior and environment variables.
- Add runtime dependencies to `pyproject.toml`; keep test dependencies in its `dev` extra. Use a project-local virtual environment.
- Keep model weights, generated media, environments, dependencies, local logs, and credentials out of source control.

## V1.1 productization scope
- The user authorizes additive model-driven development controls and session Job Center in `director/product`, selected by the launcher with VITE_PRODUCT_WORKSPACE=1. This supersedes prompt/seed-only limits only for validated bounded product requests; the legacy endpoint stays fixed. Never accept arbitrary nodes, paths, repository code or unknown custom nodes.
- Only the original Wan preview is execution validated; other declared combinations are experimental. H3 remains a metadata candidate with no transfer authorization or runnable adapter. Native audio/continuation require model-specific validation; do not show unsupported controls or silently drop audio.
- Product routes require the existing manager/Host/Origin checks. Preserve session-only automatic launcher credentials. Current job history is bounded and session-only.
- Removal/cleanup requires explicit fresh exact-inventory confirmation, owned paths, hash verification and shared-reference protection. Unknown/unregistered orphan/cache files and user media are never automatic deletion targets. No real asset removal belongs in validation.
- Activity Console is redacted application events, not a terminal. Developer Terminal remains reviewed design only; no remote shell or inherited secrets. Real downloads, production provisioning and redistribution remain disabled.
